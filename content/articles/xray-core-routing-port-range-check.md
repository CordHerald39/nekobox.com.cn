Xray-core 按端口分流不生效时，先确认写的是目标端口、来源端口，还是本地入站端口。官方路由文档分别用 port、sourcePort 和 localPort 表示这三种条件。把网站服务端口写到 sourcePort，可能导致规则始终不命中；改动前应记录请求实际使用的端口和入站标签。

## 三个字段各看哪个位置

`port` 匹配目标端口，例如应用要连接的 HTTPS 服务端口。`sourcePort` 匹配连接来源端口；它通常不能代替目标服务端口。`localPort` 匹配本地入站使用的端口，官方特别提到入站监听一个端口范围时的用途。三个位置即使偶尔出现相同数字，也仍是不同条件。

端口支持单个正整数、以连字符连接的闭合区间，以及逗号分隔的组合；取值须小于 65536。例如 `"443,8000-8100"` 表示 443，加上包含 8000 和 8100 在内的区间。它不是从 443 一直匹配到 8100，也不是给核心新增监听端口。

下面是加入已有路由规则的目标端口属性片段。保留该规则原有的入站限制和有效出站标签；这不是可独立使用的完整规则：

```json
{
  "port": "443,8000-8100"
}
```

如果需求只是匹配目标服务，不必同时增加 `sourcePort` 和 `localPort`。附加条件越多，越需要确认每个条件都满足；不要为了让配置看起来完整而把三个字段填成同一个值。

## 组合条件为什么容易漏匹配

官方说明，同一条规则指定多个属性时，这些属性必须同时满足。例如规则已有 `inboundTag` 与 `network`，增加端口后，请求还要来自指定入站、使用指定网络，并落在目标端口范围内，才会命中。TCP 的 443 与 UDP 的 443 不能仅凭端口号相同就当成同一条测试连接。

同样，协议字段与传输层网络字段也不是一回事。网页显示 HTTPS，并不足以说明当前连接一定是 TCP。先看实际连接记录，再检查 `network`，不要凭应用名称猜测连接方式。

## 从一条明确请求开始验证

1. 备份当前配置，记录规则所在位置、出站标签与运行核心版本。
2. 选一条已知入站、目标地址和目标端口的测试连接，先用原配置保存访问结果。
3. 仅修改目标端口条件，保留其余规则，执行核心配置校验后重载。
4. 新建连接，核对访问日志与实际出站；不要复用修改前已经建立的长连接。
5. 再测一个范围外端口，以及范围两端的请求。目标服务必须确实在相应端口提供服务，否则连接失败无法单独证明规则问题。

没有测试服务器时，可以从现有正常业务的端口着手，不必随意开启本地监听或扩大入站访问范围。端口条件只决定路由匹配，不会自动配置目标防火墙，也不保证出站协议支持对应流量。

## 未命中时按顺序缩小范围

先查看前面是否已有较宽的规则处理了请求，再确认请求实际进入的入站标签。随后比较目标端口、来源端口和本地端口，排除记错位置。最后检查组合条件是否太严，以及使用的出站标签是否真实存在。

如需暂时去掉端口条件作对照，只在原本就有限定目标或入站的规则上操作，避免把范围意外扩大到全局。若改动导致其他请求出站异常，恢复备份中的完整规则及位置，校验重载后复测正常业务。

基础规则顺序可参考 [Xray-core 路由规则检查](/articles/xray-core-routing-rules/)；修改前的语法检查见 [Xray-core 配置校验](/articles/xray-core-config-test/)。核心来源见 [Xray-core 独立页面](/software/xray-core/)。
