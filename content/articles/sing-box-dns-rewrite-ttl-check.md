sing-box 的 rewrite_ttl 用来改写 DNS 响应中的 TTL。它适合在限定范围内检查返回记录的有效期，不会直接修复上游无法连接，也不意味着所有应用都会立即丢弃旧地址。调整前先确认请求经过当前 DNS 规则，再保留原始响应作为对照。

## 放在 DNS 规则动作里检查

官方 DNS Rule Action 文档在 `route` 动作中列出 `rewrite_ttl`，并说明其作用是改写 DNS 响应 TTL。`route` 会把请求交给指定服务器，`server` 必须指向已有 DNS 服务器的标签。TTL 改写和选择哪台服务器是不同的设置，测试时应保留正在正常工作的服务器标签。

文档还列出了 `route-options` 等动作，以及分别带有版本标记的新字段。不要因为网页展示了某项新功能，就认为已安装核心支持整个示例。先记录核心版本，按对应版本检查动作语法；本文只讨论 `rewrite_ttl` 的局部调整，不要求采用页面中的其他新动作。

下面是加入一条已存在、已限定域名范围的 DNS `route` 规则的单个属性。它是 JSON 属性片段，不是完整规则；原有匹配条件、`action` 和有效的 `server` 标签均须保留：

```json
{
  "rewrite_ttl": 60
}
```

这里的 `60` 是用于对照的秒数示例，并非对所有域名的推荐值。不要把属性放进连接路由的 `route.rules` 后期待 DNS 响应发生变化，也不要把它误写到无关的 DNS 服务器连接字段中。

## 按顺序完成小范围试验

1. 备份实际生效的配置，记录目标域名、查询类型和原始响应 TTL。
2. 找到负责该域名的现有 DNS 规则，核对其顺序和服务器标签；先不改匹配条件与上游地址。
3. 只增加或修改 `rewrite_ttl`，通过当前核心的配置校验后重载。
4. 让测试客户端重新发起同类型查询，保存响应记录和核心日志，确认请求仍经过预期规则。
5. 用一个不命中该规则的域名作对照，检查改写有没有意外扩大范围。

若拿到的响应带有剩余 TTL，要同时记录查询时间和是否命中其他缓存。直接比较两次相隔很久的数字，可能混入缓存倒计时的影响。测试时保留返回地址与响应状态，不能只看 TTL 一个字段。

## 数字没变时先看请求路径

应用可能使用独立 DNS，也可能继续复用已有连接；这两种情况下，修改核心 DNS 规则未必会改变眼前的应用行为。先检查查询是否进入 sing-box，再核对较早规则是否已处理请求，随后检查观测工具是否查询了预期的本地服务。

`disable_cache` 另有禁用当前查询缓存相关行为的定义，不能把它和 `rewrite_ttl` 当成相同开关。为了定位 TTL 改写，先保留缓存设置；若后续确需检查缓存，也应另起一轮对照，避免同时改变变量。较长的 TTL 还可能使下游更久保留旧地址，较短值也不能保证应用立即重连。

## 怎样撤销这次修改

恢复原来的 `rewrite_ttl` 值，或在原配置没有该属性时删除新增属性，校验并重新加载。继续使用相同目标验证解析和应用连接，保存恢复后的响应作为记录，不必连带删除正常的 DNS 服务器列表。

涉及服务器类型时，参考 [sing-box DNS 配置迁移](/articles/sing-box-dns-server-migration/)；排查缓存边界时，可看 [independent_cache 检查](/articles/sing-box-dns-independent-cache-check/)。软件来源见 [sing-box 独立页面](/software/sing-box-android/)。
