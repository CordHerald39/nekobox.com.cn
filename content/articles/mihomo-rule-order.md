mihomo 中某条规则写得正确，却一直没有命中，先检查它上方有没有更早匹配的规则。官方文档说明，规则按从上到下的顺序匹配，顶部优先级更高。定位时要查看客户端实际加载的配置，而不只是订阅文件里最初的内容。

## 三类规则的作用

`DOMAIN` 匹配完整域名；`DOMAIN-SUFFIX` 匹配域名后缀及相应子域；`MATCH` 无需条件，匹配所有请求。通常应将兜底规则放在具体规则之后，否则后面的规则可能没有机会被检查。

下面是说明顺序的局部片段，使用保留示例域名，不是完整配置，也不会提供任何代理节点：

```yaml
rules:
  - DOMAIN,api.example.com,DIRECT
  - DOMAIN-SUFFIX,example.com,REJECT
  - MATCH,DIRECT
```

在这一片段中，`api.example.com` 先匹配第一条；`www.example.com` 可以匹配第二条；其他未被前面规则匹配的目标才会落入最后一条。测试自己的服务时，应替换为自己有权访问的目标，并使用配置中确实存在的策略。

## 按实际配置定位覆盖关系

1. 备份当前可用配置，记下内核版本与规则模式。
2. 检查运行时合并后的规则列表，确认本地覆写、自定义规则或脚本有没有插入更早的条目。
3. 在列表中查找受影响域名、相关后缀、规则集合以及兜底 MATCH。
4. 只调整一条规则的位置，重新加载后新建连接，观察命中的规则与出站。

已有长连接可能继续使用旧决策。验证时关闭目标应用的测试连接再重新发起请求；不要直接用原先播放中的流量判断规则是否生效。

## IP 规则为什么会牵涉 DNS

官方文档指出，匹配目标 IP 类规则时可能触发 DNS 解析。`no-resolve` 用于跳过该次规则匹配所需的解析，但更早阶段已经取得的地址仍可能参与匹配。它不是关闭全部 DNS 的开关，也不应不加区分地放到所有规则后面。

另一个边界是 UDP 支持：文档说明，如果请求为 UDP，而候选代理节点不支持 UDP，可能继续向下匹配。因此不能仅凭规则文本位置推断所有流量都会走同一路径。

## 验收与回滚

用一个具体域名、一个对应子域和一个无关目标分别验证，保存命中记录。结果不符合预期时恢复备份，检查模式、规则集合内容与实际请求目标。升级内核同时发生问题时，再参阅[mihomo 配置版本迁移](/articles/mihomo-config-version-migration/)，避免一次更改版本、规则和 DNS。
