mihomo 的 cache-algorithm 控制 DNS 缓存使用的算法。官方文档列出 lru 和 arc，其中 lru 是默认值。遇到重复查询变慢或切换配置后结果不一致时，可以做受控对照；仅凭字段名不能判断哪种算法在当前设备上更快，也不能用它代替解析服务器故障排查。

## 两个取值分别是什么

`lru` 对应 Least Recently Used，`arc` 对应 Adaptive Replacement Cache。文档展示了 `dns.cache-algorithm: arc` 的写法，同时在字段说明中注明默认值是 `lru`；示例值和默认值要分开看。本文没有提供两者的速度、命中率或内存占用结论，这些需要结合设备和实际查询负载测量。

这个字段位于 `dns` 段，和 `nameserver`、`fallback` 等字段处于同一层级。修改算法不会替你更换解析服务器地址，也不是关闭所有应用 DNS 缓存的指令。浏览器、操作系统及上游解析服务器仍可能有各自的缓存，排查时要先弄清观测的是哪一层。

## 修改前留下可比的基线

1. 保存现有配置与核心版本，记录实际生效的 `cache-algorithm`，不要只看编辑器里尚未重载的文件。
2. 选择一组平时访问的域名，包含重复访问的目标和少量首次查询目标；固定查询类型与测试顺序。
3. 记录当前网络、DNS 服务器和路由策略，测试期间保持这些条件一致。
4. 确认测试请求进入 mihomo 的 DNS 链路。仅测试一个自行使用加密 DNS 的浏览器，不能证明核心缓存的表现。

下面是合并到已有配置中的 DNS 片段。保留原有服务器和其他字段，不要用片段替换整个 DNS 段：

```yaml
dns:
  cache-algorithm: arc
```

先执行当前核心提供的配置校验，再重新加载。若校验提示未知字段或取值错误，恢复原文件，按正在运行的核心文档检查支持情况；不要为了让配置通过而同时修改其他 DNS 字段。

## 对照时看什么

对同一批域名按相同顺序查询，分别记录首次与重复查询的结果、耗时和错误。重新加载后是否保留已有缓存，需要以当前核心行为为准，不能假定两个测试轮次天然拥有相同缓存状态。每轮应写明启动或重载过程，避免把缓存冷热差异误算成算法差异。

如果耗时下降但地址异常，仍需检查上游和域名策略；如果重复查询结果正常但应用连接失败，应继续检查连接日志。一次网页打开更快只是一条观测，可能受到连接复用、网页缓存与网络波动影响，不能直接证明更换算法改善了整个代理链路。

Fake-IP 模式还涉及映射关系。不要把切换缓存算法和调整 Fake-IP 过滤、地址范围一起进行，否则结果变化后很难确定原因。对照结果不足以支持调整时，保留默认配置通常更容易维护。

## 无收益时恢复原设置

将值恢复为备份中的原值，原本未显式配置则恢复省略状态；文档注明默认值是 `lru`。再按相同流程重新校验和加载。记录回退后的表现，保留有明确差异的查询记录；无需为一次无收益的试验长期保留额外设置。

解析路径可结合 [mihomo DNS 配置检查](/articles/mihomo-dns-config-check/) 排查；需要区分真实地址与映射时，看 [Fake-IP 过滤检查](/articles/mihomo-dns-fake-ip-filter/)。官方软件入口见 [mihomo 页面](/software/mihomo/)。
