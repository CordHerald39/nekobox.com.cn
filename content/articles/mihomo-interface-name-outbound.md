电脑同时连接有线、无线或 VPN 时，应用已经进入 mihomo，出站却走了另一张网卡，可以检查顶层 `interface-name`。官方把它定义为 mihomo 的流量出站接口。它解决的是核心向外建立连接的路径，不能用来改变手机连接代理端口的监听地址。

## 先确认是哪一段走错了

保存当前配置，记录运行核心、客户端合并后的配置、测试目标与实际出站。先确认连接记录里有该请求：如果应用绕过了 mihomo，修改出口网卡没有作用。若客户端接管正常，再检查主机有哪些活动接口，以及目标网卡能否到达出站服务器。

`bind-address` 控制入站监听；`interface-name` 控制流量出口，两者不能互换。局域网设备接不进来的问题仍应按 [mixed-port 局域网连接](/articles/mihomo-mixed-port-lan-connect/) 排查，别把出口绑定当作开放端口的开关。

## 在生成后的配置中核对字段

官方示例使用以下顶层字段。`en0` 只是文档中的接口名称，实际填写本机当前存在的网卡名；不要把网卡 IP、远端节点地址或代理组名称放进这里：

```yaml
interface-name: en0
```

这是一行配置片段，合并到现有配置并保留节点、DNS 和规则。Linux 可用 `ip link show`、`ip address show` 查看接口与地址；其他系统通过网络设置或对应的接口查询工具核对。客户端可能重写配置，因此应查看核心真正加载的值。

接口存在也不代表具有目标所需的默认路由。VPN 接口、容器网卡和物理网卡的路由范围可能不同，必须结合系统路由表检查。本文不承诺所有客户端或平台都支持同样的绑定行为。

## 用一个新连接验收

1. 通过现有客户端的配置校验，确认字段没有被合并规则删除，再按原方式重载。
2. 关闭测试应用的旧连接，重新请求同一个目标，记录命中规则、代理出站与本地出口。
3. 在目标接口观察是否出现对应连接，并与修改前的路径对照；不要只看客户端显示的延迟。
4. 若绑定后连接失败，查接口是否已断开、路由是否可达，再恢复原字段与配置。

确认新连接使用目标接口且业务响应正常，才算这次绑定达到目的。仅有配置检查成功不足以证明出口变化；TLS 或远端认证失败则转向对应层，不继续扩大监听范围。涉及路由选择可继续看 [mihomo 规则顺序](/articles/mihomo-rule-order/)；升级后行为变化时先核对 [配置版本迁移](/articles/mihomo-config-version-migration/)。
