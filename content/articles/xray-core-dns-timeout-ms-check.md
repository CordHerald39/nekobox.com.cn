Xray-core DNS 查询等待过久时，可以先记录是哪台解析服务器超时，再检查它的 timeoutMs。官方文档将这个字段定义为 DNS 服务器超时时间，单位为毫秒，默认 4000 ms。它不等于网页加载的总时限，也不能让一个本来不可达的服务器恢复连接。

## 字段位于单个服务器对象

`timeoutMs` 属于 `dns.servers` 中的 DNS 服务器对象。下面只演示这个对象中的单个属性，不能替代完整服务器配置；保留原来的 `address`、`domains`、查询策略和其他字段。

```json
{
  "timeoutMs": 4000
}
```

这里使用文档注明的默认数值说明单位，不是要求所有网络都显式设置它。`4000` 表示四秒，不能把数字误当成秒数，也不要给它加上文档未规定的字符串单位。

缩短等待可能让较慢但可用的响应更早失败，延长等待也可能只是更久才收到同一个错误。应依据固定目标的日志做选择，不能把“越短越快”或“越大越稳定”当成通用结论。

## localhost 是明确例外

官方说明，`timeoutMs` 不对 `localhost` DNS，也就是系统 DNS 生效；该模式跟随 Go 的 DNS 超时行为，具体路径还可能受 cgo 与 pure Go 的差异影响。如果当前服务器是 `localhost`，反复改这个字段不构成有效的超时对照。

先核对实际生效的服务器类型。如果请求被另一条域名策略送到了系统 DNS，修改某个未参与查询的远端服务器对象，也不会改变本次等待。

## 排查时分三段记录

1. 保存配置副本、核心版本、测试域名和查询类型，记录真正参与查询的服务器及其 `timeoutMs`。
2. 对同一目标重复少量查询，记录每次开始、失败或返回的时间，不要只记浏览器最终报错时间。
3. 检查后备查询是否发生。按当前文档的默认串行流程，前一台失败后可能继续尝试下一台，因此总等待未必等于一台服务器的时限。
4. 只在目标服务器对象中调整一个值，通过当前核心校验并重载，再用相同条件对照。
5. 查询返回后另看目标连接耗时；DNS 成功与代理握手、网页下载是不同阶段。

如果启用了其他查询方式或改变了后备条件，记录这些设置后再分析，不能把所有部署都按简单的串行相加计算。缓存命中也可能绕开一次远端等待，所以每次结果都应注明是否实际发出了查询。

## 先找不可达原因，再决定时限

固定目标持续超时时，检查解析服务器地址、端口、协议与网络路径。加密 DNS 还可能涉及建立连接和证书验证；调大数字不会自动修正错误地址或证书问题。若只在某个网络复现，保留该网络下的日志与时间，再用同样目标比较。

无收益时恢复原值；原本省略则移除本轮新增属性。校验并重载后，再确认正常查询和后备行为保持原状。不要为排查单台服务器的等待问题直接删除整个 DNS 列表。

后备查询与结果过滤可结合 [expectedIPs 检查](/articles/xray-core-dns-expected-ips-check/) 阅读；地址类型见 [queryStrategy 检查](/articles/xray-core-dns-query-strategy/)，记录查询故障可参考 [日志配置](/articles/xray-core-log-config/)。
